# Introducing Quidra, a New Programming Language

Hello!
This time, I'd like to introduce a new programming language I developed: Quidra!

https://github.com/quidra-lang/quidra

What is your favorite programming language?
For me, I guess it's C++! I like that feeling that I'm building something kind of dangerous, haha.

This time, I tried building a programming language like that from scratch!
It's called **Quidra**, and the name comes from the Latin word **"Quidditas" ("essence")**.
Just as the name suggests, I'm building this language with the goal of stripping away unnecessary things and leaving only the "essence"—in other words, **eliminating ambiguity while making the syntax as short as possible**.
In terms of positioning, I think it can be classified as a **statically typed, compiled language** that generates native code through LLVM.
That said, you can run a program immediately with a single command like `quidra main.qui`, similar to Python, and there is also an interactive REPL whose internals use JIT compilation.

## Goals

- **Be the programming language with the highest semantic compression performance**
  - This is the key idea of Quidra. Maximizing this is the language's primary goal.
  - More concretely, the idea is to "eliminate ambiguity while making the syntax as short as possible."
  - However, the goal is not to reduce character count like code golf. The important point is: **remove meaningless tokens, but do not remove meaningful distinctions** — "Fewer meaningless tokens, not fewer meaningful distinctions."
  - The slogan is **"Maximum Meaning Per Token."**
  - For example, in C++, when you see `func(x)`, you cannot tell whether `x` is passed by reference or by value. To know that, you need to look at the function definition. Likewise, in Python, `y = x + 1` does not tell you the types of `x` or `y`. To learn the types, you may need to trace earlier lines or print them. In that sense, the code has high ambiguity.
  - In C++, you could imagine not having to write `int main` at all and simply executing statements from top to bottom like Python. Likewise, symbols such as `{}` can be unnecessary if indentation distinguishes blocks as in Python. In that sense, C++ syntax has high redundancy.
  - Quidra's idea is to eliminate as much of this ambiguity and redundancy in existing programming languages as possible.
- **Have an impact comparable to Python or C++**
  - I don't want Quidra to end as just a hobby language. Ultimately, I want it to become as well known as other programming languages.
  - I want to build it together with everyone, not by myself! **I'm looking for collaborators who resonate with the design principles and philosophy!**
- **Be easy to read for both humans and LLMs**
  - First, it uses natural-language words that humans already use frequently. This does not simply mean copying existing programming languages: there is no `\n` or `&&` either. Quidra uses `and` instead of `&&`, and `print` automatically adds a newline.
  - As a secondary effect of semantic compression, I also want to reduce LLM input/output token usage: code should be short, while still letting the reader understand the operation from that line alone. Common English words are often represented by a single token, so I think "natural language while still being LLM-friendly" is achievable.
- **Be easy for newcomers to learn**
  - For example, Python can express addition simply as `y = x + 1`, so it is easy for beginners. But once you want to do more complex things, you eventually need to learn 1) types and the value ranges of each type, 2) address/reference behavior—what is passed by value and what can be modified—and 3) bit operations. When learning at that deeper level, I think Python's exceptional syntax and black-box behavior can actually become difficult to understand for intermediate and long-term learners.
  - C++—or more precisely C—works the other way around: from the beginning, you need to understand types, address references, and bit operations to write programs. In that sense, it may be easier for intermediate and long-term learners to understand. But you also need to learn relatively difficult concepts such as pointer manipulation just to modify array values inside a function. In that sense, it is difficult for beginners.
  - So with Quidra, I want a language that works well across the beginner, intermediate, and long-term stages. More concretely: it should be relatively low-ceremony and easy to write like Python, but keep explicit types so it is easier to understand what is happening internally; complex pointer manipulation should be replaced by mechanisms such as C++-style references while still allowing people to learn the concept of addresses; and of course bit operations should still be available.
  - Assignments such as `a = b` for arrays and classes are value copies by default, meaning all values are copied. If you only want to refer to an array or class, you write that explicitly, for example `int[] &a = &b`. Even with value semantics, the compiler may internally omit a copy when copying or not copying cannot change the result. For example, when an array is passed to a function that does not modify the argument, Quidra already refers to it internally without copying. In other words, the user-facing semantics are value semantics, while the implementation can optimize the copy away. I designed details like this by imagining what would have felt more intuitive immediately after I first started learning programming.
  - Ultimately, I'd love to see Quidra used in university courses as a first programming language!

### Example Program

If we write a program for handling student grades, it looks like this.
I packed in several Quidra-like ideas at once: classes, functions that may fail, pass-by-reference, and so on!

```quidra:grades.qui
class Student
    string name
    int[] scores

    construct(string student_name, int[] student_scores)
        name = student_name
        scores = student_scores

    float average()
        int total = 0
        for score in scores
            total += score
        return float(total) / float(len(scores)) // int → float is an explicit conversion

// A function that may fail includes error in its return type
int | error parse_score(string text)
    int score = try int.parse(text) // On failure, propagate error directly to the caller
    if score < 0 or score > 100
        return error("out of range: {text}")
    return score

// int[] & = receive permission to modify the caller's array
void add_bonus(int[] &scores, int bonus)
    for &score in scores
        score = math.min(score + bonus, 100)

Student alice = Student("Alice", [72, 85, 98])
Student backup = alice // Value copy (changing alice does not change backup)
add_bonus(&alice.scores, 5) // & shows at the call site that the original object, not a copy, is passed

print("{alice.name}: {alice.average():frac=1}")
print("backup: {backup.average():frac=1}")

for text in ["88", "abc", "120"]
    match parse_score(text) // Both int and error must be handled
        int score
            print("OK {score}")
        error problem
            print("NG {problem}")
```

```text:Output
Alice: 89.0
backup: 85.0
OK 88
NG numeric parse failed
NG out of range: 120
```

A few important points:

- With `int | error`, **a function that may fail says so directly in its return type**. An exception does not secretly fly out from behind the scenes.
- The `&` in `add_bonus(&alice.scores, 5)` indicates that **the original object, not a copy, is being passed**. Conversely, if an argument has no `&`, then from the call site alone you can determine that **the callee can never modify it**.
- `Student backup = alice` is a value copy, so changing `alice` does not change `backup`.
- With `match`, the program will not compile unless both `int` and `error` are handled.

I also wrote the same operation in Python and C++ and compared the token counts. Comments are excluded; the count uses a simple lexer, and string literals—including interpolated expressions—are counted as one token.

| Language | Lines (excluding blank lines and comments) | Tokens |
|---|---:|---:|
| **Quidra** | 30 | **177** |
| Python (without type hints) | 26 | 178 |
| Python (with type hints) | 26 | 200 |
| C++ | 38 | 296 |

Quidra explicitly writes **all of the static types, mutation permissions (`&`), and failure possibility (`int | error`)**, yet its token count is almost the same as Python without type hints!
Compared with C++, it uses roughly 30–40% fewer tokens, depending on whether the contents of string interpolation expressions such as `{…}` are counted.

#include <stdexcept>
#include <string>

    std::string name;
    std::vector<int> scores;

    double average() const {
        int total = 0;
        for (int score : scores) total += score;
        return static_cast<double>(total) / scores.size();

    int score = std::stoi(text);
    if (score < 0 || score > 100) throw std::out_of_range("out of range: " + text);
    return score;
}

### Eliminating Ambiguity

In Quidra, **one symbol or keyword has only one meaning**.

| Syntax | Meaning |
|---|---|
| `=` | Copy a value (assign as an independent value) |
| `&x` | Explicitly operate on variable `x` itself rather than a copy |
| `T &` | Mutable reference |
| `const T &` | Read-only reference |
| `T \| none` | The type includes the possibility that there is no value |
| `T \| error` | The type includes the possibility of failure |
| `try` | Propagate `error` to the caller, and nothing else |
| `T(value)` | Explicit type conversion when `T` is numeric; for classes, `T(...)` is a constructor call |
| `and` / `or` / `not` | Logical operations, for bool only |
| `AND` / `OR` / `XOR` / `NOT` / `<<` / `>>` | Bit operations, for fixed-width integers only |
| `match` | Branching that must exhaustively handle every case |

Let's look at this concretely.

#### Pass by Reference or Pass by Value: `f(x)` vs. `f(&x)`

In C++, a function that modifies its argument and one that does not look exactly the same at the call site.

```cpp
void add_one(int& value) { value += 1; }  // Modifies
void show(int value) { /* ... */ }        // Does not modify

add_one(count);  // At the call site
show(count);     // they look exactly the same
```

In Quidra, if a function modifies an argument, **the caller must also write `&`**.

```quidra:ref.qui
void add_one(int &value)
    value += 1

int count = 1
add_one(&count)
print(count)
```

```text:Output
2
```

If you forget `&`, you get a compile error.

```text
ref.qui:5:9: error[WRITE_CAPABILITY] Argument reference form must match parameter.
```

Conversely, adding `&` when calling a pass-by-value function produces the same error.
So **an argument without `&` can never be modified by the callee**.
Writing through a read-only reference such as `const int &` is also a compile error.

#### Assignment Copies Values; References Are Explicit with `&`

```quidra:copy.qui
int[] a = [1, 2, 3]
int[] b = a
b[0] = 9
print("a[0] = {a[0]}, b[0] = {b[0]}")

int[] &c = &a
c[0] = 7
print("a[0] = {a[0]}, c[0] = {c[0]}")
```

```text:Output
a[0] = 1, b[0] = 9
a[0] = 7, c[0] = 7
```

Because `b = a` is a copy, modifying `b` does not change `a`.
Only when you want a reference do you make it explicit on both the type and right-hand side, as in `int[] &c = &a`.
In Python, `b = a` shares the same list, so `b[0] = 9` also changes `a[0]`.

#### No Implicit Type Conversions

```quidra
int big = 300
int8 small = big
```

```text
error[TYPE_MISMATCH] Expected int8 but received int.
```

When you want to change the type, you write it explicitly, such as `int8(big)`.
Even then, if the value is out of range, **execution stops with a runtime error rather than silently wrapping the value**.

```text
Quidra runtime error[NUMERIC_CAST_RANGE] at 2:14: numeric cast outside destination range
```

In C++, the same code compiles without even a warning and silently changes the value.

```cpp
int big = 300;
int8_t small = big;  // No warning even with -Wall -Wextra; small becomes 44
```

Likewise, adding an `int` and a `float` is an error unless you write an explicit conversion such as `float(i) + d`, and converting from `float` to `int` requires you to specify the rounding method itself, such as `math.round` or `math.floor`.

#### Representing "Failure" and "No Value" in the Type

```quidra:parse.qui
int | error parse_twice(string text)
    int value = try int.parse(text)
    return value * 2

for text in ["21", "12abc"]
    match parse_twice(text)
        int doubled
            print(doubled)
        error problem
            print("NG: {problem}")
```

```text:Output
42
NG: numeric parse failed
```

`try` propagates only `error` to the caller.
If you forget a branch in `match`, compilation fails with `error[MATCH_EXHAUSTIVE]`.
And if you receive the result directly without using `match`, as in `int doubled = parse_twice(text)`, failure is not silently ignored—the program stops on that line with a runtime error.

Incidentally, C++'s `std::stoi("12abc")` **silently returns `12`**.
Python's `int("12abc")` does throw an exception, but you cannot tell from the function type alone that an exception might occur.

#### Separating Logical and Bitwise Operations

Quidra has no `&&`, `||`, or `!`.
Logical operations use `and` / `or` / `not`, while bitwise operations use uppercase `AND` / `OR` / `XOR` / `NOT`.

```quidra:permission.qui
uint8 can_read = 4
uint8 can_write = 2
uint8 can_run = 1

uint8 permission = can_read OR can_write
bool writable = (permission AND can_write) != 0
bool runnable = (permission AND can_run) != 0

print(bin(permission))
if writable and not runnable
    print("read/write only")
print(bin(permission << 1))
print(bin(NOT permission))
```

```text:Output
00000110
read/write only
00001100
11111001
```

Using `and` with `uint8` or `AND` with `bool` is a type error.
You also cannot use an integer directly as a condition, as in `if count`; only `bool` can be used as a condition.

#### Shadowing Is Forbidden

```quidra
int total = 0
for i in range(3)
    int total = i
```

```text
error[SHADOWING] Name is already visible or reserved.
```

You cannot hide an outer name with another declaration inside an inner scope.
That means adding nearby code later cannot silently change what an existing name refers to.

### Eliminating Redundancy

Let's start with the classic Hello World.

```quidra:hello.qui
print("Hello, World!")
```

| Language | Lines (excluding blank lines) | Tokens |
|---|---:|---:|
| **Quidra** | 1 | **4** |
| Python | 1 | 4 |
| C++ | 5 | 20 |
| Java | 5 | 26 |

There is no need for a `main` function like C++ or Java, no `#include`, and no class.
There are several other things you do not have to write:

- **No `main` required:** statements execute from top to bottom. In fact, defining a function named `main` is an error.
- **No `{}` or `;` required:** blocks are expressed with indentation. Indentation is fixed at **four spaces**; tabs or two spaces are errors, so formatting cannot drift.
- **`print` automatically adds a newline:** use `write` when you do not want one. There is no escape sequence such as `\n`; a backslash is just a character, so Windows paths can be written directly. When you need a newline character, write `{ENTER}`.
- **No `self` or `this` required:** fields can be read and written directly inside methods.
- **Type inference with `auto`:** you can infer a type from an expression whose type is uniquely determined, as in `auto doubled = count * 2`.

```quidra:newline.qui
print("line 1")
print("line 2")
write("no newline")
write(" continues")
print("")
print("first{ENTER}second")
print("C:\Users\quidra\notes.txt")
```

```text:Output
line 1
line 2
no newline continues
first
second
C:\Users\quidra\notes.txt
```

By the way, `auto count = 3` is an error.
Quidra refuses to arbitrarily decide whether `3` should be `int` or `int8`. That is another example of eliminating ambiguity.

## Benchmarks

I also ran benchmarks using existing programming languages.
The ten languages compared were Python, C++, Rust, Go, Java, TypeScript, Kotlin, Swift, Zig, and Quidra.
The evaluation used the following five perspectives.

| Evaluation | In simple terms |
|---|---|
| Semantic compression | How much certain meaning can be packed into each token |
| Language quality | Runtime speed, file size, safety, and language design |
| LLM learnability | Whether an LLM can learn the language's rules from a specification and use them |
| LLM proficiency | Whether an LLM can write practical programs without being given documentation |
| Ecosystem | Richness of libraries, tools, and community |

Deterministically measurable parts—runtime speed, file size, safety tests, and compiling/testing LLM-generated code—are handled mechanically through shell and Python execution.
Nondeterministic parts, such as annotating the meaning of code, evaluating language design, researching the ecosystem, and measuring how well an LLM can work with the language, are handled by LLMs.
Score aggregation, normalization, and ranking are done by scripts, although the scores for each LLM learnability condition and some LLM proficiency metrics use the values assigned directly by an LLM according to the scoring rubric.
Because the five evaluations measure very different things, I deliberately did not combine them into a single overall ranking.

I mainly used Claude Sonnet 5 as the LLM.
Of course, I used the API so that sessions could not peek at each other.
More specifically, each LLM worker—the session responsible for an evaluation—basically handles only one language, and runs inside a Docker container with networking disabled, so it cannot see results for other languages or previous runs. Only the ecosystem investigation uses web search.
(I just wanted to run a benchmark, but I ended up spending tens of thousands of yen on it... 😭)

To avoid making the evaluation favorable to Quidra, I also designed it under the following rules:

- Metrics, weights, and tasks are **fixed before measurement**.
- Tasks are not created from Quidra's syntax or features, and **features Quidra cannot express are not removed from the tasks**.
- There are no Quidra-specific metrics; the same rules are applied to all ten languages.

Details of the benchmark methods and results—including breakdowns for each metric and the reasons behind LLM judgments—are published in the repository.

### Semantic Compression

This is the main event!

Semantic compression was measured using **44 tasks across 20 areas**, including variable declarations, references, overflow, error handling, generics, concurrency, and FFI (calling functions from other languages).
For each of the ten languages, an LLM wrote the smallest possible code fragment for each task.
The LLM then annotated each fragment with things such as "what meaning is determined locally" and "how many interpretations remain," and a script aggregated the counts.

There are six metrics.
The five metrics other than coverage—the quality metrics—are normalized relatively so that the best language among the ten gets 100 and the worst gets 0.

| Metric | What it measures | Weight | Quidra |
|---|---|---:|---:|
| Semantic density | Number of locally determined meanings per token | 20% | **100 (1st)** |
| Uniqueness | How many interpretations remain from that line alone | 25% | **100 (1st)** |
| Locality | How often you must look elsewhere to determine meaning | 20% | 34.45 (5th) |
| Hidden semantic cost | Things that happen even though they are not written, such as implicit conversions | 20% | 81.48 (2nd) |
| Feature efficiency | Number of rules required per feature | 15% | 36.46 (7th) |
| Coverage | Percentage of the 44 tasks expressible using standard features | Harmonic mean component | 81.82 (9th) |

#### Semantic Density

This measures how many meanings are determined **locally, without looking elsewhere**, per token.
For example, `const int n = 7` tells you locally that the value is a value, cannot be reassigned, is initialized, and has type `int`.
The metric counts such locally determined meanings and divides by the token count.

Across the 31 tasks that all languages could express, the results were:

| Language | Determined meanings / tokens | Semantic density | Score |
|---|---:|---:|---:|
| **Quidra** | 133 / 808 | **0.1646** | **100** |
| Swift | 108 / 751 | 0.1438 | 70.49 |
| Zig | 121 / 893 | 0.1355 | 58.69 |
| Kotlin | 106 / 783 | 0.1354 | 58.52 |
| Go | 109 / 863 | 0.1263 | 45.65 |
| Rust | 117 / 1015 | 0.1153 | 29.99 |
| Python | 79 / 714 | 0.1106 | 23.42 |
| TypeScript | 90 / 884 | 0.1018 | 10.88 |
| C++ | 95 / 973 | 0.0976 | 4.96 |
| Java | 98 / 1041 | 0.0941 | 0 |

<font color="#e0245e">**Quidra ranked 1st in semantic density.**</font>
Python is an interesting case: it has the fewest tokens (714), but also the fewest meanings determined locally (79), so its density is low.
This shows clearly that **shorter is not automatically better**.

The token counts were produced by the LLM, but I also recounted them using the same simple regex-based lexer for all languages, and Quidra still ranked 1st.
Whitespace and indentation are not counted, so indentation-based languages such as Quidra and Python do receive a slight advantage because they do not need `{}`.

#### Uniqueness

This measures how many possible interpretations remain when you look at that line alone—for example, whether something is modified, copied, how it fails, or how a type conversion behaves.
If only one interpretation remains, the score is perfect.

Quidra was <font color="#e0245e">**the only language in which all 31 tasks expressible by every language had exactly one remaining interpretation**</font>.

The C++ `func(x)` example from the beginning was measured directly in the benchmark.
After creating an array `x`, calling `f(x)`, and then reading `x[0]`, the workers counted how many possibilities remain if you look only at the call site: read-only? modified? resized? reference retained? copied?

| Language | Remaining interpretations |
|---|---:|
| **Quidra** | **1** |
| Rust | 1 |
| Swift | 2 |
| Python | 3 |
| Go / Java / TypeScript | 4 |
| C++ / Kotlin / Zig | 6 |

Because Quidra has no `&` in the call, it is determined to be pass-by-value and unmodifiable by the callee.
In C++, by contrast, pass-by-value, pass-by-reference, and const-reference all look the same at the call site, so all candidates remain.
This count is taken directly from the LLM workers' annotations. Because a different worker counted each language, there are some inconsistencies even between languages with similar mechanisms, such as Java and Kotlin.

Overflow for `x += 1` was also evaluated.
Quidra always stops with a runtime error, so there is one interpretation.
Rust and Zig can behave differently depending on build mode, so they were counted as two.
C++ was judged as undefined behavior.

#### Locality, Hidden Semantic Cost, and Feature Efficiency

Quidra did not rank 1st in the remaining three quality metrics, especially locality and feature efficiency.

- **Locality (5th, 34.45):** how many times you need to look elsewhere—function declarations, type definitions, imported modules, standard-library specifications, and so on—to determine meaning. Of the 17 lookups counted for Quidra, 11 were for variables that the task statement said had been declared elsewhere. The remaining lookups were for standard-library guarantees such as "files are closed automatically" and "`task.all` preserves result order." However, workers were inconsistent about whether to count these predeclared-variable lookups at all—Go did not count them, while Swift counted them per variable—so this difference should be taken with some caution. Zig ranked 1st.
- **Hidden semantic cost (2nd, 81.48):** how many things happen even though they are not explicitly written, such as implicit type conversion or hidden mutation. Almost all of the costs counted for Quidra were things such as overflow or out-of-range access causing runtime errors even though that behavior is not visible in the syntax. Zig ranked 1st.
- **Feature efficiency (7th, 36.46):** the number of rules—syntax forms, implicit rules, exceptional rules, and so on—required per feature. Quidra was penalized for global implicit rules such as overflow checking and value copying, as well as exceptional rules such as "`private` can only be attached to class members." It required about 1.8 rules per point, where each task is worth two points. Swift, the 1st-place language, required about 0.95.

#### Coverage

```text
int a = 5
print(a)
```

If a language had only one type, `int`, and only one function, `print`, its semantic compression would obviously be high.
What matters is how many things the language can express while preserving that semantic compression.

So I measured **the percentage of the 44 tasks, worth 88 total points, that can be expressed using standard features**.
Tasks that cannot be expressed remain in the denominator, so languages with fewer features score lower.

| Rust | 98.86 |
| Swift | 97.73 |
| Zig | 94.32 |
| Go | 90.91 |
| Java | 90.91 |
| Kotlin | 90.91 |
| TypeScript | 82.95 |
| **Quidra** | **81.82** |
| Python | 77.27 |

Quidra scored 81.82, ranking 9th.
Honestly, this is the biggest weakness...

The tasks that could not be expressed, or could only be partially expressed, were:

- Closures that capture local variables
- Runtime dispatch through inheritance or interfaces (two tasks)
- Array slices
- Sorting with a custom comparison function, such as descending order
- User-defined destructors
- Exporting functions callable from C
- Partially: transforming optional values without `if` or `match`, and `private` functions visible only within a module

On the other hand, references, overflow behavior, error handling, concurrency, and calling C functions all received full credit.

Interestingly, if quality Q remained unchanged and <font color="#e0245e">**Quidra could express just one additional task, it would mathematically edge past Zig into 1st place in semantic compression**</font>, haha.
That said, the difference would be only 0.05 points, so rather than focusing on the exact ranking, I think the important trend is: "quality Q is 1st, coverage is the issue."
There is plenty of room to grow!

#### Overall Semantic Compression Score

I define the weighted average of the five quality metrics as **quality Q**, then take the harmonic mean of quality Q and coverage C to measure whether a language achieves semantic compression while still offering broad functionality.

```math
\text{Overall Score} = \frac{2 \times Q \times C}{Q + C}
```

The harmonic mean makes it difficult for the overall score to become high if only one side is high.
For example, C++ has coverage 98.86, tied for 1st, but quality Q is 11.36, so its overall score is 20.38, the lowest.

The conclusion is that Quidra ranked 2nd, behind Zig.

Summarizing the results:

- **Matrix multiplication was faster than C++, Rust, and Zig!** Quidra: 1.212 s, C++: 1.338 s, Rust: 1.345 s, Zig: 1.359 s.
- Factorial, floating-point arithmetic, and dot product were almost as fast as C++, within 5%.
- Across the geometric mean of the 11 operations, **Quidra was about 16.5× faster than Python**.
- On the other hand, it was about 1.85× slower than C++ by geometric mean, or about 1.4× slower if file I/O is excluded.
- **File I/O took 12.49 seconds, about 45× slower than Zig.** It also used about 1.6 GB of memory, which is obviously wrong, so this absolutely needs improvement 😭

Quidra was measured with integer-overflow and array-bounds checks **always enabled**.
C++ with `-O2` does not have those checks in the first place, while Rust with `-O` and Zig with `ReleaseFast` also disable overflow checks, so Quidra carries some overhead there.
On the other hand, Quidra internally uses Clang `-O3`, which is more aggressive than the C++ `-O2` setting, so that may also contribute to results such as the matrix multiplication difference.

Startup time, measured with Hello World, was about 1.95 ms for Quidra, roughly the same as C++ at about 1.98 ms and Go at about 1.93 ms.
Compared with JVM languages such as Java at about 30.8 ms and Kotlin at about 50.1 ms, Quidra starts very quickly.

Build time was also around 0.13–0.21 seconds for most programs, making it the second-fastest compiled language after Go at about 0.13 seconds.
For comparison, C++ took 1.3–1.8 seconds and Zig about 15 seconds.
Under the scoring formula, Python receives a perfect score because it does not require a build, while every compiled language ends up close to zero, so the raw build times are probably more meaningful here.

#### Safety

I ran 37 deliberately nasty programs in every language—integer overflow, narrowing conversion, out-of-bounds array access, division by zero, NaN, infinite recursion, malformed input, and so on.
The system mechanically classified where each problem was caught: at compile time, at runtime with a controlled stop, as a crash, as undefined behavior, or as a silent bug that produced the wrong answer without noticing.

| Metric | Quidra | Rank |
|---|---:|:---:|
| Type safety | 74.58 | **1st** |
| Silent-bug resistance | 91.18 | **1st** |
| Debuggability | 66.67 | 2nd |
| Boundary safety | 54.55 | 3rd |
| Early error detection | 59.81 | 5th |
| Runtime safety | 41.67 | 5th |
| Memory safety | 44.44 | 7th |
| Malicious-input resistance | 50.71 | 8th |

<font color="#e0245e">**Type safety and silent-bug resistance ranked 1st.**</font>
Out of 37 programs, Quidra had three silent bugs and zero cases of undefined behavior. C++, by comparison, had 15 cases of undefined behavior and 11 silent bugs.
Quidra was also the **only language that stopped every tested integer-overflow and narrowing-conversion case, including runtime-input patterns, with an error message**.
However, Rust and Zig were again measured in release modes—`-O` and `ReleaseFast`—where overflow checking is disabled. Rust debug builds and Zig `ReleaseSafe` would stop those cases too, so measurement conditions matter a lot here.

Memory safety and runtime safety scored relatively low.
The reason was cases such as out-of-bounds array access and infinite recursion.
Quidra did stop them with explicit error codes, for example:

```text
Quidra runtime error[INDEX_BOUNDS] at 5:15: index -1 outside length 5
```

But the message did not match the benchmark's detection regex, which expected phrases such as `out of bounds`, so it was classified as a "crash."
Still, using more conventional wording is friendlier for humans too, so I would like to improve this.

### LLM Suitability

I measured how easy the language is for LLMs in two ways.

#### Learnability

This evaluation gives an LLM a language specification—a subset of the rules—and measures whether it can **learn the language on the spot and write correct code**.
To prevent prior knowledge of familiar languages from becoming an advantage, keywords are replaced with meaningless words such as `glim` and `fenta`, and fictional rules are added.

| Condition | Description | Weight | Quidra |
|---|---|---:|---:|
| I1 | Replace keywords with fictional words | 20% | 96 |
| I2 | Replace standard-library names too | 20% | 71 |
| I3 | Change surface syntax such as delimiters | 15% | **100** |
| I4 | Learn and use a fictional new rule from the spec | 20% | **100** |
| I5 | Combine rules taught separately | 15% | 34 |
| I6 | Give familiar words unfamiliar meanings, e.g. swap `for` and `while` | 10% | 12 |

The result was 74.70, ranking 10th.
Quidra performed well on I1–I4, including perfect scores on I3 and I4, but fell sharply on I5 and I6.
Most failures came from being pulled toward C-family syntax: braces, semicolons, `for (int v : values)`, `void main()`, and so on.

**Note:** The I5 and I6 tasks were generated by a separate LLM worker for each language.
For many other languages such as Python, C++, and Go, the task became "implement a toy language's rules using a familiar language."
For Quidra, the task instead became "combine Quidra's own syntax and write it in Quidra."
That made the condition somewhat harsher for Quidra, so I would appreciate it if you keep that in mind when reading the result.

#### Proficiency

This evaluation gives the LLM **no documentation at all** and asks it to write practical programs.
The tasks are SVM, GMM, and automatic differentiation, each under two conditions—implement from a specification or port from a C++ reference implementation—with three trials each, for 18 trials total.
When the code fails to compile or tests fail, the error is returned to the model and it gets up to three repair attempts.
Correctness is checked using hidden tests that the LLM never sees.
The only Quidra information given to the model is the language name and the build command.

The result was 5.32, ranking 9th.
In all 18 trials, the first generated program failed to compile, and even across 72 generations including repairs, **not a single program passed the tests**.
Most failures came from importing syntax from other languages.

| What the LLM tends to write | Quidra compiler response |
|---|---|
| Define `int main()` | `error[RESERVED_MAIN] Function name 'main' is reserved.` |
| Write `import math` | `error[STANDARD_NAMESPACE_IMPORT] Standard namespace 'math' is always available and cannot be imported.` |
| Rust-style `fn add(a: i64, b: i64) -> i64` | `error[PARSE_ERROR] fn requires '<Result>' before its parameter list.` |
| Use C-style `{` blocks | `error[LEX_ERROR] Unexpected character in source.` |

This result is reasonable.
Quidra was released only recently, Claude Sonnet 5 has not been trained on it, and if you ask it to write Quidra without seeing any documentation, it is not surprising that it cannot produce a working program.

Interestingly, **Zig also scored 4.00, ranking 10th, and likewise produced zero successful programs**.
Its failures came from the latest standard-library API in Zig 0.16 differing from what the model remembered.
In other words, this evaluation reflects "how much the model knows about the language, especially the latest version" more strongly than "how easy the language is to write."
The score difference between Quidra and Zig comes from LLM judging discretion; practically speaking, they are tied.

In fact, almost all of Quidra's failures violated rules that are explicitly written in the LLM guide (`docs/spec/llm-guide.md`) or language specification: top-level statements are the entry point, standard namespaces are not imported, blocks use four-space indentation, and the return type is written before the function name.
In the future, I would like to measure a condition where the guide is provided.

### Ecosystem

Finally, I evaluated the maturity of libraries, tools, and community.
An LLM researched the web and scored the findings using a fixed rubric.

Quidra scored **32.50 and ranked 10th**: 9.0 for the external ecosystem and 56.0 for the toolchain.
Because the language was released only recently, there are almost no third-party libraries, production adoption cases, Q&A-site discussions, and so on.
Of course it ranks last, haha.

Even so, the official documentation, browser-based Playground, formatter, REPL, and dependency lockfile with SHA-256 hashes received some credit as a toolchain.
This is exactly the part where **I need everyone's help!**

### Benchmark Caveats

**Important notes:**

- The rankings are simply an ordering of the measurements from this run; they are not claims of statistically significant superiority.
- The code fragments and annotations used for semantic compression were produced by LLMs and were not verified by compilation. Different workers annotated each language, and their counting styles vary somewhat. In particular, Zig, Quidra, and Swift are so close that one annotation could change their order.
- Runtime performance was measured on shared GitHub Actions runners, so treat it as a comparison under the same environment rather than an absolute speed measurement.
- The programs used for language quality—10 languages × 11 programs—were prepared on my side, including the Quidra versions. All languages use the same algorithms and inputs, and outputs are mechanically verified.
- LLM-suitability results depend strongly on the model used, Claude Sonnet 5, and on what that model already knows.

## What I Want to Do Next

This benchmark made Quidra's room for improvement very clear.

- **Increase coverage:** closures, interfaces for runtime dispatch, array slicing, sorting with comparison functions, and so on.
- **Speed up file I/O:** being 45× slower than Zig is, well...
- **Make error messages friendlier to LLMs:** for example, if someone writes `&&`, tell them "use `and`."
- **Grow the ecosystem:** libraries, editor extensions, and more.

Coverage is especially tempting: according to the current calculation, adding support for just one more task would be enough to reach 1st place in semantic compression.
That is where I want to start!

I developed a language called Quidra with the goal of **Maximum Meaning Per Token**.

On the other hand, the model's prior knowledge of Quidra and the ecosystem are still very limited. Those are areas I want to grow together with everyone from here.
