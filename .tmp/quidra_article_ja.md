こんにちは！
今回は，私が開発した新プログラミング言語「Quidra」の紹介になります！

https://github.com/quidra-lang/quidra

みなさんの好きなプログラミング言語は何でしょうか？
私はC++ですかね！ヤバいものを作っているような，あの感覚が好きです笑

今回は，そんなプログラミング言語を私がゼロから作ってみました！
名前は「**Quidra（クイドラ）**」と言い，**ラテン語の「Quidditas（本質）」が由来**です．
名前の通り，余計なものを削ぎ落として「本質」だけを残す，つまり「曖昧性を排除しつつ，できるだけ短い構文を作る」ことを目標に，このプログラミング言語を作っています！
立ち位置としては，**静的型付けのコンパイル型言語**（LLVMでネイティブコードを生成）に分類されるかなと思います．
とはいえ，`quidra main.qui` の1コマンドでPythonのようにすぐ実行できますし，対話的に試せるREPL（中身はJITコンパイル）もあります．

## 目標

- **意味圧縮の性能が最も高いプログラミング言語**
  - これが今回の肝になります．この言語の一番の目標はこれを最大化することです．
  - 具体的には「曖昧性を排除しつつ，できるだけ短い構文を作る」という考え方です．
  - ただし，コードゴルフのように文字数を削ることが目的ではありません．**意味のないトークンは削るけれど，意味のある区別は削らない**（Fewer meaningless tokens, not fewer meaningful distinctions）というのがポイントです．
  - スローガンは「1トークンあたりの意味最大化」（Maximum Meaning Per Token）
  - 例えば，C++の `func(x)` の `x` は参照渡しか値渡しかわかりません．したがって，それを知るには関数の定義部分を見るという手間があります．また，Pythonの `y = x + 1` は `x`・`y` の型が定まりません．型を知るには，前の行を遡ってみるか，printで表示してみる必要があります．よって，曖昧性が高いと見ることができます．
  - C++の `int main` は書かなくてもPythonのように上から順に実行する，という形式でも動きます．また，`{}` などもPythonのようにインデントで区別すれば不要です．よって，C++の構文は冗長性が高いと言えます．
  - これら既存のプログラミング言語の「曖昧性」や「冗長性」をできる限り無くしていくというのがQuidraの考え方です．
- **PythonやC++級の波及力を持つこと**
  - 単なる趣味言語では終わらず，最終的には他のプログラミング言語ぐらい有名な言語にしたいと思っています．
  - 私だけではなくみんなで作っていきたいです！ **設計理念・思想に共感できる人をコラボレーターとして募集しています！**
- **人間・LLMにとって読みやすい**
  - まず，人間がよく使っている自然言語を使います．単に既存プログラミング言語と同じというわけではなく，`\n` とか `&&` とかも無しです（`&&` の代わりに `and` を使いますし，`print` は自動で改行してくれます）．
  - また，意味圧縮の副次効果として，LLMの入力・出力トークン消費量を削減する（短いコードであり，かつその1行を見るだけで処理を理解できる）ことも狙っています．よく使われる英単語は多くの場合1トークンで表現されるため，「自然言語でありながらLLMにも扱いやすい」は両立できると思っています．
- **新規参入者にとって学びやすい**
  - 例えば，Pythonは `y = x + 1` で簡単に足し算が表現できます．つまり，初学者にとっては学びやすいです．しかし，より複雑な処理をやりたいと思うと，①型（それぞれの型における値の範囲），②アドレス参照（どこまでが値渡しでどこまで書き換えられるか），③ビット演算という部分まで学ぶ必要が出てきます．このように深く学ぼうとした時は，Pythonの例外的構文やブラックボックス性が理解しにくく，中期・長期の学習者にとっては逆に扱いにくいと考えています．
  - 一方，C++（というかC言語）は最初から型，アドレス参照，ビット演算を理解していないと，書けないような言語になっています．そういう点では，中期・長期の学習者にとっては理解しやすいかもしれません．しかし，ポインタ操作などの学習難易度高めなものを覚えないと，関数内での配列の値代入すらできません．そういう意味では，初期の学習者にとっては扱いにくいです．
  - そこで，Quidraでは初期・中期・長期と幅広く扱えるような言語にしたいと思っています．具体的には，Pythonのように比較的儀式が少なく手軽に書けるが，型も残しつつ（内部で何しているかわかりやすい），複雑なポインタ操作はC++の参照渡しなどで代用する（しかしアドレスの概念は学べる），もちろんビット演算などもできる，といったような感じです．
  - 配列やクラスの代入 `a = b` も原則値渡し（値が全部コピーされる）として，もし配列やクラスを参照したいだけなら `int[] &a = &b` のように明示的に書くようにする（値渡しでも，コピーしてもしなくても結果が変わらない場面では，コンパイラが内部でコピーを省略できる設計になっている．例えば，引数を書き換えない関数に配列を渡すときは，現状でもコピーせずに参照している．つまりユーザ体験としては値渡しだが内部で最適化される．）など，私がプログラミングを学び始めた直後のことを想像し，より直感的な方で処理が行われるように工夫しました．
  - 最終的に，大学の講義とかで初プログラミングの授業としても使われてほしいなと思っています！


## Quidraの概要

Quidraは「1トークンあたりの意味最大化」を第一目標としています．
実際に例を見ながら確認していきましょう！

:::note info
この記事のコードは，Quidra 0.3.0（言語仕様 0.2）で動作確認しています．
0.3.0 は現在 `develop` ブランチにあり，最新のリリース版やPlayground（0.2系）では一部のコードが動かないので，試すときは `develop` ブランチからビルドしてください．
:::

### プログラム例

学生の成績を扱うプログラムを実際に書いてみると，以下のようになります．
クラス，失敗するかもしれない関数，参照渡しなど，Quidraらしさを一通り詰め込んでみました！

```quidra:grades.qui
class Student
    string name
    int[] scores

    construct(string student_name, int[] student_scores)
        name = student_name
        scores = student_scores

    float average()
        int total = 0
        for score in scores
            total += score
        return float(total) / float(len(scores)) // int → float は明示変換

// 失敗しうる関数は戻り値の型に error が入る
int | error parse_score(string text)
    int score = try int.parse(text) // 失敗なら error をそのまま呼び出し元へ
    if score < 0 or score > 100
        return error("out of range: {text}")
    return score

// int[] & = 呼び出し元の配列を書き換える権限をもらう
void add_bonus(int[] &scores, int bonus)
    for &score in scores
        score = math.min(score + bonus, 100)

Student alice = Student("Alice", [72, 85, 98])
Student backup = alice // 値コピー（alice を変えても backup は変わらない）
add_bonus(&alice.scores, 5) // & で「コピーではなく本体を渡す」ことを呼び出し側でも示す

print("{alice.name}: {alice.average():frac=1}")
print("backup: {backup.average():frac=1}")

for text in ["88", "abc", "120"]
    match parse_score(text) // int と error の両方を必ず処理する
        int score
            print("OK {score}")
        error problem
            print("NG {problem}")
```

```text:実行結果
Alice: 89.0
backup: 85.0
OK 88
NG numeric parse failed
NG out of range: 120
```

ポイントをいくつか挙げると，

- `int | error` のように，**失敗するかもしれない関数は，戻り値の型にそう書きます**．例外が裏でこっそり飛んでくることはありません．
- `add_bonus(&alice.scores, 5)` の `&` は，**コピーではなく本体を渡している**という印です．逆に `&` が無い引数は，**呼び出し先で絶対に書き換えられない**と，呼び出し側だけで確定します．
- `Student backup = alice` は値のコピーなので，`alice` を変えても `backup` は変わりません．
- `match` では，`int` と `error` の両方を処理しないとコンパイルが通りません．

同じ処理をPythonとC++でも書いて，トークン数を比べてみました（コメントを除き，簡易的な字句解析器（レキサ）で計測．文字列リテラルは，埋め込み式も含めて1トークンと数えています）．

| 言語 | 行数（空行・コメントを除く） | トークン数 |
|---|---:|---:|
| **Quidra** | 30 | **177** |
| Python（型ヒントなし） | 26 | 178 |
| Python（型ヒントあり） | 26 | 200 |
| C++ | 38 | 296 |

Quidraは，静的な型・書き換えの権限（`&`）・失敗の可能性（`int | error`）を**すべて書いた上で**，型ヒントなしのPythonとほぼ同じトークン数になっています！
C++と比べると，約3〜4割少ないです（文字列の埋め込み式 `{…}` の中身を数えるかどうかで変わります）．

```python:grades.py
import copy


class Student:
    def __init__(self, name: str, scores: list[int]):
        self.name = name
        self.scores = scores

    def average(self) -> float:
        return sum(self.scores) / len(self.scores)


def parse_score(text: str) -> int:
    score = int(text)
    if score < 0 or score > 100:
        raise ValueError(f"out of range: {text}")
    return score


def add_bonus(scores: list[int], bonus: int) -> None:
    for i in range(len(scores)):
        scores[i] = min(scores[i] + bonus, 100)


alice = Student("Alice", [72, 85, 98])
backup = copy.deepcopy(alice)
add_bonus(alice.scores, 5)

print(f"{alice.name}: {alice.average():.1f}")
print(f"backup: {backup.average():.1f}")

for text in ["88", "abc", "120"]:
    try:
        score = parse_score(text)
        print(f"OK {score}")
    except ValueError as problem:
        print(f"NG {problem}")
```

```cpp:grades.cpp
#include <algorithm>
#include <cstdio>
#include <stdexcept>
#include <string>
#include <vector>

struct Student {
    std::string name;
    std::vector<int> scores;

    double average() const {
        int total = 0;
        for (int score : scores) total += score;
        return static_cast<double>(total) / scores.size();
    }
};

int parse_score(const std::string& text) {
    int score = std::stoi(text);
    if (score < 0 || score > 100) throw std::out_of_range("out of range: " + text);
    return score;
}

void add_bonus(std::vector<int>& scores, int bonus) {
    for (int& score : scores) score = std::min(score + bonus, 100);
}

int main() {
    Student alice{"Alice", {72, 85, 98}};
    Student backup = alice;
    add_bonus(alice.scores, 5);

    std::printf("%s: %.1f\n", alice.name.c_str(), alice.average());
    std::printf("backup: %.1f\n", backup.average());

    for (std::string text : {"88", "abc", "120"}) {
        try {
            int score = parse_score(text);
            std::printf("OK %d\n", score);
        } catch (const std::exception& problem) {
            std::printf("NG %s\n", problem.what());
        }
    }
    return 0;
}
```

### 曖昧性の排除

Quidraでは，**1つの記号・キーワードには1つの意味だけ**を持たせています．

| 書き方 | 意味 |
|---|---|
| `=` | 値のコピー（独立した値として代入） |
| `&x` | 変数 `x` そのもの（コピーではなく本体）を扱うことを明示 |
| `T &` | 書き換え可能な参照 |
| `const T &` | 読み取り専用の参照 |
| `T \| none` | 「値がない」ことが型に含まれる |
| `T \| error` | 「失敗する」ことが型に含まれる |
| `try` | `error` を呼び出し元へ伝播する（それ以外の意味はない） |
| `T(value)` | 明示的な型変換（`T` が数値型のとき．クラスの `T(...)` はコンストラクタ呼び出し） |
| `and` / `or` / `not` | 論理演算（bool専用） |
| `AND` / `OR` / `XOR` / `NOT` / `<<` / `>>` | ビット演算（固定幅の整数専用） |
| `match` | すべての場合を漏れなく処理する分岐 |

具体的に見ていきましょう．

#### 参照渡しか値渡しか：`f(x)` と `f(&x)`

C++では，書き換える関数も書き換えない関数も，呼び出し側の見た目は同じです．

```cpp
void add_one(int& value) { value += 1; }  // 書き換える
void show(int value) { /* ... */ }        // 書き換えない

add_one(count);  // 呼び出し側は
show(count);     // まったく同じ見た目
```

Quidraでは，関数が引数を書き換える場合は，**呼び出し側にも `&` が必要**です．

```quidra:ref.qui
void add_one(int &value)
    value += 1

int count = 1
add_one(&count)
print(count)
```

```text:実行結果
2
```

`&` を付け忘れると，コンパイルエラーになります．

```text
ref.qui:5:9: error[WRITE_CAPABILITY] Argument reference form must match parameter.
```

逆に，値渡しの関数に `&` を付けても同じエラーになります．
つまり，**`&` が付いていない引数は，呼び出し先で絶対に書き換えられません**．
また，読み取り専用の参照（`const int &`）を通して書き込もうとした場合も，コンパイルエラーになります．

#### 代入は値のコピー，参照は `&` で明示

```quidra:copy.qui
int[] a = [1, 2, 3]
int[] b = a
b[0] = 9
print("a[0] = {a[0]}, b[0] = {b[0]}")

int[] &c = &a
c[0] = 7
print("a[0] = {a[0]}, c[0] = {c[0]}")
```

```text:実行結果
a[0] = 1, b[0] = 9
a[0] = 7, c[0] = 7
```

`b = a` はコピーなので，`b` を書き換えても `a` は変わりません．
参照したいときだけ，`int[] &c = &a` のように型にも右辺にも `&` を付けて明示します．
Pythonの `b = a` は同じリストを共有するので，`b[0] = 9` で `a[0]` も変わってしまいますね．

#### 暗黙の型変換はしない

```quidra
int big = 300
int8 small = big
```

```text
error[TYPE_MISMATCH] Expected int8 but received int.
```

型を変えたいときは `int8(big)` のように明示します．
その場合も，値が範囲外なら**実行時エラーで止まり，値が勝手に回り込むことはありません**．

```text
Quidra runtime error[NUMERIC_CAST_RANGE] at 2:14: numeric cast outside destination range
```

C++で同じことをすると，警告すら出ずにコンパイルが通り，こっそり値が変わります．

```cpp
int big = 300;
int8_t small = big;  // -Wall -Wextra でも警告なし．small は 44 になる
```

ほかにも，`int` と `float` の足し算は `float(i) + d` のように明示しないとエラーですし，`float` から `int` への変換は `math.round` や `math.floor` のように**丸め方まで明示**する必要があります．

#### 「失敗」と「値がない」を型で表す

```quidra:parse.qui
int | error parse_twice(string text)
    int value = try int.parse(text)
    return value * 2

for text in ["21", "12abc"]
    match parse_twice(text)
        int doubled
            print(doubled)
        error problem
            print("NG: {problem}")
```

```text:実行結果
42
NG: numeric parse failed
```

`try` は `error` だけを呼び出し元に伝播します．
`match` で分岐を書き忘れると `error[MATCH_EXHAUSTIVE]` でコンパイルエラーになります．
また，`match` を使わずに `int doubled = parse_twice(text)` のように受け取った場合も，失敗が黙って無視されることはなく，その行で実行時エラーとして止まります．

ちなみにC++の `std::stoi("12abc")` は，**黙って `12` を返します**．
Pythonの `int("12abc")` は例外を投げてくれますが，関数の型を見ただけでは「例外が飛ぶかもしれない」ことはわかりません．

#### 論理演算とビット演算を分ける

Quidraには `&&` も `||` も `!` もありません．
論理演算は `and` / `or` / `not`，ビット演算は大文字の `AND` / `OR` / `XOR` / `NOT` です．

```quidra:permission.qui
uint8 can_read = 4
uint8 can_write = 2
uint8 can_run = 1

uint8 permission = can_read OR can_write
bool writable = (permission AND can_write) != 0
bool runnable = (permission AND can_run) != 0

print(bin(permission))
if writable and not runnable
    print("read/write only")
print(bin(permission << 1))
print(bin(NOT permission))
```

```text:実行結果
00000110
read/write only
00001100
11111001
```

`uint8` に `and` を使ったり，`bool` に `AND` を使ったりすると型エラーになります．
また，`if count` のように整数をそのまま条件に使うこともできません（`bool` 以外は条件にならない）．

#### 名前の隠蔽（シャドーイング）を禁止

```quidra
int total = 0
for i in range(3)
    int total = i
```

```text
error[SHADOWING] Name is already visible or reserved.
```

外側の名前を内側で隠すことはできません．
なので，後から近くにコードを書き足しても，前に書いた名前の参照先がこっそり変わることがありません．

### 冗長性の排除

まずはお決まりのHello Worldです．

```quidra:hello.qui
print("Hello, World!")
```

| 言語 | 行数（空行を除く） | トークン数 |
|---|---:|---:|
| **Quidra** | 1 | **4** |
| Python | 1 | 4 |
| C++ | 5 | 20 |
| Java | 5 | 26 |

C++やJavaのような `main` 関数も，`#include` も，クラスも要りません．
その他にも，以下のような「書かなくていいもの」があります．

- **`main` は不要**：上から順に実行されます（むしろ `main` という名前の関数を作るとエラーです）．
- **`{}` も `;` も不要**：ブロックはインデントで表します．インデントは**スペース4つに固定**で，タブや2スペースはエラーになるので，書き方の「揺れ」も起きません．
- **`print` は自動で改行**：改行したくないときは `write` を使います．`\n` のようなエスケープはなく，バックスラッシュはただの文字なので，Windowsのパスもそのまま書けます．改行文字が必要なときは `{ENTER}` と書きます．
- **`self` や `this` は不要**：メソッドの中では，フィールドを直接読み書きできます．
- **型推論 `auto`**：`auto doubled = count * 2` のように，型が決まる式から推論できます．

```quidra:newline.qui
print("1行目")
print("2行目")
write("改行なし")
write("で続く")
print("")
print("first{ENTER}second")
print("C:\Users\quidra\notes.txt")
```

```text:実行結果
1行目
2行目
改行なしで続く
first
second
C:\Users\quidra\notes.txt
```

ちなみに，`auto count = 3` はエラーになります．
`3` が `int` なのか `int8` なのかを勝手に決めない，というのも曖昧性の排除ですね．


## ベンチマーク

既存のプログラミング言語も用いて，ベンチマークを実施してみました．
比較した言語は，Python，C++，Rust，Go，Java，TypeScript，Kotlin，Swift，Zig，Quidraの10言語です．
評価は，次の5つの観点で行いました．

| 評価 | ざっくり言うと |
|---|---|
| 意味圧縮性能 | 1トークンあたりに，どれだけ確かな意味を詰め込めるか |
| 言語品質 | 実行速度・ファイルサイズ・安全性・言語設計 |
| LLM学習容易性 | 仕様を渡されたLLMが，その言語のルールを学んで使えるか |
| LLM実用性 | LLMが何も見ずに，実用的なプログラムを書けるか |
| エコシステム | ライブラリ・ツール・コミュニティの充実度 |

実行速度やファイルサイズ，安全性テスト，LLMが書いたコードのコンパイル・テストなど，決定論的に評価できる部分は機械（シェル実行・Python実行）に任せ，コードの意味の注釈や言語設計の評価など非決定論的な部分や，エコシステムの調査のように検索が必要な部分，そしてLLMがその言語を扱えるかを測る目的の項目はLLMに任せています．
スコアの集計・正規化・順位付けはスクリプトで行っています（ただし，LLM学習容易性の各条件のスコアと，LLM実用性の一部の指標は，LLMが採点基準に沿って付けた値をそのまま使っています）．
また，5つの評価は性質がまったく違うので，全部を足し合わせた「総合順位」はあえて作っていません．

LLMには主にClaude Sonnet 5を使用しました．
もちろんですが，他のセッションを覗き見しないようにAPIを利用しています．
具体的には，LLMのワーカー（評価作業を担当するLLMのセッション）1つが担当するのは基本的に1言語だけで，ネットワークを切ったDockerコンテナの中で動かしているので，他の言語の結果や過去の実行結果は見られません（エコシステムの調査だけはWeb検索ありです）．
（ベンチマークやりたかっただけなのに，数万円使ってしまった...泣）

また，Quidraに有利な評価にならないよう，次のようなルールで設計しています．

- 指標・重み・課題は，**測定の前に固定する**
- Quidraの構文や機能をもとに課題を作らない．**Quidraにできない機能も課題から外さない**
- Quidra専用の指標は作らず，10言語すべてに同じルールを適用する

ベンチマークの方法や結果の詳細（各指標のスコアの内訳や，LLMの判断理由を含む）は，リポジトリに公開しています．

### 意味圧縮性能

今回一番の目玉になります！

意味圧縮性能は，変数の宣言，参照，オーバーフロー，エラー処理，ジェネリクス，並行処理，FFI（他の言語の関数の呼び出し）など，**20分野・44個の課題**を用意し，10言語それぞれでLLMに最小限のコード断片を書かせて測っています．
そのコード断片に対して，「どんな意味が，その場で確定しているか」「解釈が何通り残るか」などをLLMが注釈し，その数をスクリプトで集計しています．

指標は次の6つです．
網羅性以外の5つの指標（以下，品質指標）は，10言語の中で最も良い言語を100，最も悪い言語を0として正規化しています（相対評価です）．

| 指標 | 何を見るか | 重み | Quidra |
|---|---|---:|---:|
| 意味密度 | 1トークンあたり，その場で確定する意味の数 | 20% | **100（1位）** |
| 一意性（意味の確定性） | その1行だけを見て，解釈が何通り残るか | 25% | **100（1位）** |
| 局所性 | 意味を確定するのに，他の場所を何回見に行く必要があるか | 20% | 34.45（5位） |
| 隠れた意味コスト | 書いていないのに起きること（暗黙の変換など）の数 | 20% | 81.48（2位） |
| 機能効率 | 機能1つあたりに必要なルールの数 | 15% | 36.46（7位） |
| 網羅性 | 44課題のうち，標準の機能で書ける割合 | 調和平均 | 81.82（9位） |

#### 意味密度

1トークンあたりに，その場で（他の場所を見ずに）確定する意味がいくつあるか，です．
例えば `const int n = 7` からは，「値である」「再代入できない」「初期化済み」「`int` 型」といった意味がその場で読み取れます．
こういった「その場で確定する意味」の数を，トークン数で割ったものです．

全言語で書けた31課題で比較すると，次のようになりました．

| 言語 | 確定した意味 / トークン数 | 意味密度 | スコア |
|---|---:|---:|---:|
| **Quidra** | 133 / 808 | **0.1646** | **100** |
| Swift | 108 / 751 | 0.1438 | 70.49 |
| Zig | 121 / 893 | 0.1355 | 58.69 |
| Kotlin | 106 / 783 | 0.1354 | 58.52 |
| Go | 109 / 863 | 0.1263 | 45.65 |
| Rust | 117 / 1015 | 0.1153 | 29.99 |
| Python | 79 / 714 | 0.1106 | 23.42 |
| TypeScript | 90 / 884 | 0.1018 | 10.88 |
| C++ | 95 / 973 | 0.0976 | 4.96 |
| Java | 98 / 1041 | 0.0941 | 0 |

<font color="#e0245e">**Quidraが意味密度1位**</font>です！
面白いのはPythonで，トークン数は最少（714）ですが，その場で確定する意味も最少（79）なので，密度は低くなっています．
**短ければ良いわけではない**，というのがよくわかりますね．

※ トークン数はLLMが数えていますが，念のため全言語共通の簡易レキサ（正規表現）で数え直しても，Quidraが1位なのは変わりませんでした．なお，空白やインデントは数えないルールなので，インデントでブロックを表すQuidraやPythonは，`{}` の分だけ少し有利です．

#### 一意性（意味の確定性）

その1行だけを見たときに，意味（書き換えるのか，コピーされるのか，失敗の仕方，型変換の仕方など）の解釈が何通り残るか，です．
1通りに決まれば満点です．

Quidraは，<font color="#e0245e">**全言語で書けた31課題すべてで，解釈が1通りに決まった唯一の言語**</font>でした！

冒頭で書いたC++の `func(x)` の例も，実際にベンチマークで測っています．
配列 `x` を作って `f(x)` を呼び，その後 `x[0]` を読むとき，呼び出し側だけを見て「読むだけ？書き換える？サイズを変える？参照を持ち続ける？コピーされた？」などの候補が何通り残るかを数えたものです．

| 言語 | 残る解釈の数 |
|---|---:|
| **Quidra** | **1** |
| Rust | 1 |
| Swift | 2 |
| Python | 3 |
| Go / Java / TypeScript | 4 |
| C++ / Kotlin / Zig | 6 |

Quidraは `&` が無いので「値渡しで，呼び出し先からは書き換えられない」と1通りに確定します．
一方でC++は，値渡し・参照渡し・const参照渡しのどれでも呼び出しの見た目が同じなので，候補がすべて残ります．
※ この数はLLMワーカーの注釈そのままです．言語ごとに別のワーカーが数えているので，JavaとKotlinのように似た仕組みの言語でも数え方がぶれている所があります．

また，`x += 1` のオーバーフローも，Quidraは常に実行時エラーで止まる（1通り）のに対し，RustやZigはビルドモードによって挙動が変わる（2通り），C++は未定義動作，と判定されました．

#### 局所性・隠れた意味コスト・機能効率

残りの3つの指標では1位を取れませんでした（特に局所性と機能効率は伸び悩みました）．

- **局所性（5位，34.45）**：意味を確定するために，他の場所（関数の宣言，型の定義，import先，標準ライブラリの仕様など）を何回見に行く必要があるか，です．Quidraで数えられた17回のうち11回は，「課題文で別の場所に宣言済みとされた変数」の宣言を見に行く分で，残りは「ファイルは自動でクローズされる」「`task.all` は結果の順序を保つ」のような標準ライブラリの約束事などでした．ただ，この「宣言済みの変数」を数えるかどうかはワーカーごとにバラバラ（Goは数えず，Swiftは変数ごとに数える）なので，ここの差は少し割り引いて見てください．1位はZigです．
- **隠れた意味コスト（2位，81.48）**：暗黙の型変換や見えない書き換えなど，「書いていないのに起きること」の数です．Quidraで数えられたのは，ほぼ「オーバーフローや範囲外アクセスで実行時エラーになることが，構文からは見えない」というものでした．1位はZigです．
- **機能効率（7位，36.46）**：機能1つあたりに必要なルール（構文の種類・暗黙のルール・例外的なルールなど）の数です．Quidraは，オーバーフロー検査や値のコピーといった言語全体の暗黙のルールや，「`private` はクラスのメンバーにしか付けられない」のような例外的なルールがカウントされ，1点（1課題＝2点）あたり約1.8個でした（1位のSwiftは約0.95個）．

大事なのは，意味圧縮の性能を保ったまま，どれだけ多くのことを書けるかです．

そこで，44課題（1課題2点，88点満点）のうち，**標準の機能だけで書ける割合**を「網羅性」として測りました．

ちなみに，品質Qはそのままで<font color="#e0245e">**あと1課題でも書けるようになれば，計算上はZigをわずかに上回って意味圧縮性能1位**</font>になります笑

伸びしろですね！

#### 総合評価

5つの品質指標の加重平均を**品質Q**として，品質Qと網羅性Cの調和平均をとり，機能が充実しつつも意味圧縮を実現できているかの指標を出してみました．

```math
\text{総合スコア} = \frac{2 \times Q \times C}{Q + C}
```

調和平均は，片方だけが高くても全体が上がりにくい平均です．
例えばC++は網羅性が98.86（1位タイ）ですが，品質Qが11.36なので，総合は20.38（最下位）になります．

スコア（プログラムごとのサイズ比の平均）では，Pythonに次ぐ**2位**（92.32）でした（合計のバイト数ではGoの方がわずかに小さいです）．
静的型付けの言語なのに，Pythonとほぼ同じ量で書けています！

実行ファイルのサイズは，次のようになりました．

| 言語 | 成果物 | サイズ |
|---|---|---:|
| C++ | 実行ファイル | 16〜37KB |
| Swift | 実行ファイル | 27〜51KB |
| **Quidra** | **実行ファイル** | **227〜288KB** |
| Go | 実行ファイル | 2.4〜2.5MB |
| Zig | 実行ファイル | 3.6〜3.7MB |
| Rust | 実行ファイル | 4.4MB |
| Kotlin | .jar（ランタイム込み） | 5.5MB |
| Java | .class（別途JVMが必要） | 1.5〜5.9KB |
| TypeScript | .js（別途Node.jsが必要） | 1.6〜5.2KB |
| Python | なし（ソースのまま実行） | 0 |

Quidraは，ネイティブの実行ファイルを作る言語の中では，C++・Swiftに次いで3番目に小さいサイズでした．
ただし，スコアは1.70（6位）です．
これは成果物が0バイトのPythonを基準にスコアを計算しているためで，ネイティブの実行ファイルを作る言語は，いちばん小さいC++でも17点ほど，数MBあるGo・Zig・Rustは1点未満になっています（どの言語もstripなし・リンク方法もデフォルトのままなので，サイズは目安として見てください）．

#### 安全性

37個の「意地悪なプログラム」（整数オーバーフロー，縮小変換，配列の範囲外アクセス，ゼロ除算，NaN，無限再帰，壊れた入力など）を全言語で実行し，問題を「コンパイル時に検出」「実行時に検出して停止」「クラッシュ」「未定義動作」「気づかずに間違った結果を出す（サイレントバグ）」のどの段階で捕まえられたかを，機械的に判定しています．

| 指標 | Quidra | 順位 |
|---|---:|:---:|
| 型安全性 | 74.58 | **1位** |
| サイレントバグ耐性 | 91.18 | **1位** |
| デバッグのしやすさ | 66.67 | 2位 |
| 境界値の安全性 | 54.55 | 3位 |
| 早期のエラー検出 | 59.81 | 5位 |
| 実行時の安全性 | 41.67 | 5位 |
| メモリ安全性 | 44.44 | 7位 |
| 悪意ある入力への耐性 | 50.71 | 8位 |

<font color="#e0245e">**型安全性とサイレントバグ耐性は1位**</font>でした！
37個のプログラムのうち，Quidraのサイレントバグは3件，未定義動作は0件です（C++は未定義動作15件，サイレントバグ11件）．
また，整数オーバーフローと縮小変換を，**実行時の入力のパターンまで含めて，すべてエラーメッセージ付きで止められたのはQuidraだけ**でした．
ただし，RustとZigはここでもリリースビルド（`-O`・`ReleaseFast`）で測っていてオーバーフロー検査が外れているので，Rustのデバッグビルドや Zig の `ReleaseSafe` なら同じように止まります．ここは言語の差というより，測定条件の差も大きいです．

ただ，メモリ安全性や実行時の安全性は低めでした．
原因は配列の範囲外アクセスや無限再帰のケースで，Quidraはこれらをエラーコード付きで止めているのですが，

```text
Quidra runtime error[INDEX_BOUNDS] at 5:15: index -1 outside length 5
```

このメッセージが判定用の正規表現（`out of bounds` など）に一致せず，「クラッシュ」扱いになってしまいました．
とはいえ，一般的な言い回しに寄せるのは読む人にとっても親切なので，改善したいと思います．

#### 言語設計

言語設計は，LLMが指標ごとに固定の採点基準（5項目×0〜4段階）で判定しています．
なお，この8指標は，Sonnet 5が以前に集めた根拠をもとに，別のモデル（GPT-5.6 Sol）が現行の採点基準で判定し直したものです．

| 指標 | Quidra | 順位 |
|---|---:|---|
| 可読性 | 95 | **1位**（Goと同率） |
| 診断（エラーメッセージ） | 100 | **1位**（Rustと同率） |
| 依存関係のシンプルさ | 100 | **1位**（Rust・Goと同率） |
| 簡潔さ | 90 | 3位（Python・TypeScriptと同率） |
| 移植性 | 90 | 5位（Python・Rustと同率） |
| 表現力 | 85 | 7位（Javaと同率） |
| 他言語との連携（FFI） | 70 | 7位（Pythonと同率） |
| 並行処理 | 55 | 10位 |

可読性は「型・書き換え可能な参照（`&`）・制御フロー・エラーの伝播が，少ない記号で明示されている」，エラーメッセージは「安定したエラーコード，位置情報，JSON出力がある」と評価されました．
逆に並行処理は，`task.all` と `atomic.Counter` くらいしかなく，キャンセルやチャネルなどが無い点で最下位でした．

### LLM適性

LLMにとって扱いやすい言語かどうかを，2つの評価で測りました．

#### 学習しやすさ（LLM学習容易性）

LLMに言語の仕様（ルールの抜粋）を渡して，**その場で学んで正しく書けるか**を測る評価です．
事前に知っている言語が有利にならないよう，キーワードを `glim` や `fenta` のような意味のない単語に置き換えたり，架空のルールを追加したりします．

| 条件 | 内容 | 重み | Quidra |
|---|---|---:|---:|
| I1 | キーワードを架空の単語に置き換える | 20% | 96 |
| I2 | 標準ライブラリの名前も置き換える | 20% | 71 |
| I3 | 区切り記号などの，見た目の文法を変える | 15% | **100** |
| I4 | 架空の新ルールを，仕様から学んで使う | 20% | **100** |
| I5 | 別々に教えたルールを，組み合わせて使う | 15% | 34 |
| I6 | なじみのある単語に，普段と違う意味を持たせる（例：`for` と `while` を入れ替える） | 10% | 12 |

結果は74.70で10位でした．
I1〜I4（特にI3・I4は満点）では健闘したものの，I5・I6で大きく落としています．
失敗の中身を見ると，波かっこ・セミコロン・`for (int v : values)`・`void main()` のような，**C言語系の構文に引きずられてしまった**ものがほとんどでした．

:::note info
I5・I6の課題はLLMのワーカーが言語ごとに作る方式で，他の多くの言語（Python・C++・Goなど）では「おもちゃの言語のルールを，よく知っている言語で実装する」課題だったのに対し，Quidraは「Quidra自身の構文を組み合わせて書く」課題になっていました．Quidraには少し厳しい条件だったので，この点は差し引いて見てもらえると嬉しいです．
:::

#### 実用性（LLM実用性）

こちらは，LLMに**何も資料を渡さずに**，実用的なプログラムを書かせる評価です．
課題は，SVM（サポートベクターマシン）・GMM（混合ガウスモデル）・自動微分の3つで，それぞれ「仕様から実装」と「C++の参照実装から移植」の2パターン×3試行，計18試行です．
コンパイルエラーやテストの失敗があれば，その内容を返して最大3回まで修正させます．
正解の判定には，LLMに見せない隠しテストも使っています．
なお，モデルに渡したQuidraの情報は「言語名」と「ビルドコマンド」だけです．

結果は5.32で9位でした．
18試行すべてで最初のコードがコンパイルに通らず，修正を含めた72回の生成でも，**テストに通るプログラムは1本も書けませんでした**．
失敗の多くは，他の言語の書き方を持ち込んだもので，例えばこんな感じです．

| LLMが書いてしまいがちなもの | Quidraコンパイラの反応 |
|---|---|
| `int main()` を定義する | `error[RESERVED_MAIN] Function name 'main' is reserved.` |
| `import math` と書く | `error[STANDARD_NAMESPACE_IMPORT] Standard namespace 'math' is always available and cannot be imported.` |
| Rust風に `fn add(a: i64, b: i64) -> i64` と書く | `error[PARSE_ERROR] fn requires '<Result>' before its parameter list.` |
| C風に `{` でブロックを書く | `error[LEX_ERROR] Unexpected character in source.` |

当然ですが，Quidraは公開されてまだ間もない言語で，Claude Sonnet 5はQuidraを未学習なので，何も見ずに書かせると動くプログラムが1本も書けない，となるのは妥当な結果です．

面白いのは，**Zigも4.00（10位）で，同じく1本も書けなかった**ことです．
Zigの失敗は，最新版（0.16）の標準ライブラリのAPIが，モデルの記憶と食い違っていたことが原因でした．
つまりこの評価は，「言語の書きやすさ」よりも「モデルがその言語（の最新版）をどれだけ知っているか」を強く反映しています．
ちなみに，QuidraとZigの差はLLMの採点の裁量によるもので，実質的には同点です．

実は，Quidraの失敗のほとんどは，LLM向けのガイド（`docs/spec/llm-guide.md`）や言語仕様に書いてあるルール（トップレベルの文がエントリポイントになる，標準の名前空間はimportしない，ブロックは4スペースのインデントで書く，戻り値の型を先に書く）に反するものでした．
今後は，ガイドを渡した条件でも測ってみたいと思います．

### エコシステム

最後に，ライブラリ・ツール・コミュニティなどの充実度です．
LLMがWeb検索で調べた結果を，固定の基準で採点しています．

結果は，**Quidraが32.50で10位**でした（外部のエコシステム 9.0，ツールチェーン 56.0）．
リリースからまだ間もない言語なので，サードパーティ製のライブラリや本番での採用実績，Q&Aサイトの情報などはほぼゼロです．
当然の最下位ですね笑

それでも，公式ドキュメントやブラウザで動くPlayground，フォーマッタ・REPL，依存関係を固定するロックファイル（SHA-256のハッシュ付き）など，ツールチェーン自体は一定の評価をもらえました．
ここはまさに，**みなさんの力が必要なところ**です！

### ベンチマークの注意点

:::note warn
- 順位は今回の測定結果をそのまま並べたもので，統計的な優劣を主張するものではありません．
- 意味圧縮性能のコード断片と注釈はLLMによるもので，コンパイルでの確認まではしていません．また，言語ごとに別々のワーカーが注釈していて数え方も少しずつ違うので，特に上位3言語（Zig・Quidra・Swift）は，注釈1か所で順位が入れ替わる程度の接戦です．
- 実行速度はGitHub Actionsの共有ランナー上での計測なので，絶対的な速さではなく，同じ環境での比較として見てください．
- 言語品質で使ったプログラム（10言語×11本）は，Quidra版も含めて筆者側で用意したものです（全言語で同じアルゴリズム・同じ入力にそろえ，出力の正しさは機械的に検証しています）．
- LLM適性の結果は，使ったモデル（Claude Sonnet 5）とその知識に強く依存します．
:::
